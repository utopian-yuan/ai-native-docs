# 给自己项目写 AGENTS.md

根文件要让一个刚进仓库的人或 Agent 能开始工作。可以直接采用 [本仓库的根规则](../../AGENTS.md)，再由团队补上自己项目的入口。多人共用的判断写在根文件，某个包才有的行为写在该包的 AGENTS.md，随时变化的进度留在工作项。

## 从一次真实改动提取规则

挑一项近期合入的改动，请当时的开发者说明第一次读了什么、在哪一步需要找同事、跑了什么才敢交付。将能重复执行的部分写成“遇到这种任务，先查哪里，做完留下什么”。只引用仓库中真实存在的目录、命令和角色。

| 团队要回答的问题 | 适合写进规则的内容 |
| --- | --- |
| 我先读哪个文件？ | 产品目标的维护入口、接口定义的维护源、现有测试的位置。若设计与当前行为有差异，说明各自依据和负责决策的人 |
| 我能直接改到哪里？ | 按任务类型说明开工作项的条件、谁能确认范围、哪些改动会影响另一模块 |
| 两人同时做时改哪行？ | 指到任务表中的认领、依赖和交接字段，共享契约指定维护者，写清同步顺序 |
| 我怎样证明交付？ | 给出本模块真实可运行的命令或可重做的操作，并说明它覆盖哪条 AC，证据放哪里 |
| 怎样让下一位找到我？ | 指到唯一 CHANGELOG，说明交付时间、负责人与贡献者如何署名，以及怎样找到证据和对应版本 |

## 一条规则怎样写得可执行

以 CSV 导出为例，仅写“重视协作并充分测试”，接手人很难判断下一步。采用下面的写法，就能据此分工和复验。

> 修改导出字段时，接口维护者先把字段顺序和空结果约定写进工作项的 design.md；页面开发者在自己的任务行引用该约定。用包含逗号的样本跑一次导出，将解析出的列值和验证版本追加到 evidence.md。交付人在 CHANGELOG 标明各自改了哪一层。

如果项目已有跨模块协议，改为链接它的真实路径。若实际操作只适用于导出模块，就把这段放入模块规则。命令被替换或目录移动时，随改动更新对应规则和引用。

## 用一次交接检查规则

1. 让一名未参与原任务的同事或一个新 AI 会话从根 README 开始，给它工作项 ID。
2. 请它指出主状态、负责人、可认领的一项任务、最近一次真实验证，以及决定是否验收的人。
3. 再从 CHANGELOG 中选一个人的一版改动，沿链接找到证据和当时的版本。遇到两个文件给出不同答案时，团队选定一个维护位置，其余入口改成链接。

对 Codex、Claude Code 以及使用 DeepSeek、GLM 的不同客户端，都可以做这次交接练习。客户端采用专用指令文件时，从它引用根规则，以后调整团队约定只改一处。
