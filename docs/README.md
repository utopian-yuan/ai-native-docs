# 项目文档由谁维护

在这个模板仓库中，[团队规则](../AGENTS.md) 供开发者和 Agent 共用，[编写指南](guides/writing-agents.md) 帮维护者适配规则，[四件套](_templates/change/) 用于建工作项。本项目的[首版工作项](tasks/TASK-20261118-team-docs-kit/change.md)记录真实开发进度，虚构的 [CSV 导出示例](../examples/csv-export/FEAT-20261110-csv-export/change.md) 供教学使用。

## 给业务项目划分维护位置

团队可以沿用现有目录名，只需在项目 README 说明每种问题到哪里找。以下归属来自 EDTQ 的实践，按项目实际内容采用。

| 要回答什么问题 | 资料放哪里 | 什么时候更新 |
| --- | --- | --- |
| 产品应该怎样表现？ | 产品需求、原型、验收条件，如 `docs/product/` | 需求负责人确认改变范围或语义时 |
| 系统实际怎么工作？接口由谁维护？ | 版本对应的代码、接口定义、架构和决策，如 `docs/architecture/` | 模块边界、契约或长期决策改变时 |
| 几个工作项按什么顺序做？ | 跨任务计划，如 `docs/plan/` | 里程碑、依赖或分工调整时 |
| 这次谁改、进展如何、验了什么？ | 对应 FEAT、BUG 或 TASK 的四件套 | 执行人更新任务和证据，负责人维护主状态 |
| 这套操作别人怎么复做？ | 可重复执行的指南，如 `docs/guides/` | 新步骤或命令经实际核对后 |
| 哪份材料是来源、哪次结论只对当时有效？ | 原始资料、带日期的报告、被替代的方案，可分别置于 `references/`、`reports/`、`archive/` | 保留来源版本、适用范围和替代入口 |
| 哪次交付改变了什么，由谁完成？ | 根 [CHANGELOG](../CHANGELOG.md) | 每次阶段交付或改版时追加，链接对应工作项与证据 |

同一事实由一处维护，其他文档链接到它。例如修复「空结果丢失表头」时，在 BUG 里记录复现和验证；如果团队决定让空结果改为提示消息，再由需求负责人更新产品口径并同步接口约定。归档旧方案时保留适用时间和替代入口，已被其他文档引用的工作项目录可以原地关闭。
